# Как участвовать (для студентов)

## 0. Один раз
- Аккаунт GitHub с реальным именем в профиле (ФИО или Фамилия И.) и группой в bio — иначе оценка не найдёт Вас.
- Сделайте **Fork** репозитория `iitu-2026-1-sem/django-2026` в свой аккаунт и клонируйте свой fork.
- `git remote add upstream https://github.com/iitu-2026-1-sem/django-2026.git` — чтобы забирать свежий `main`.

## 1. Цикл одной фичи
1. Найдите Issue с меткой `good first issue` / `week-N` без исполнителя, напишите комментарий «беру» (или создайте Issue по шаблону «Фича» — преподаватель одобрит).
2. Обновите main: `git checkout main && git pull upstream main`.
3. Ветка: `git checkout -b feat/<номер>-<кратко>` (пример: `feat/12-ticket-priority`).
4. Код + тесты + миграции. Проверка: `make check` (ruff + pytest) — должно быть зелёным.
5. Коммиты по-русски или по-английски, но по делу: `feat(tickets): приоритет заявки (#12)`.
6. `git push origin feat/12-ticket-priority` → **Pull Request** в `iitu-2026-1-sem/django-2026:main`, заполните шаблон, в описании `Closes #12`.
7. Дождитесь ревью. Правки — новыми коммитами в ту же ветку. После merge удалите ветку.

## 2. Что такое «готово» (Definition of Done)
- Фича работает и покрыта тестом (минимум 1 тест на happy-path + 1 на ошибку/права).
- `make check` зелёный, CI на PR зелёный.
- Миграции есть и применяются с нуля (`python manage.py migrate` на чистой базе).
- Нет секретов, нет закомментированного мусора, нет `print()` — используйте `logging`.
- В PR: что сделано, как проверить, скриншот (если UI).

## 3. Ревью и оценка
Преподаватель ревьюит в порядке очереди PR (обычно в течение 2 рабочих дней). Баллы по силлабусу: работоспособность 4 · качество кода 3 · защита 3.
На защите (практика/СРОП) Вы объясняете свой код и вносите изменение по требованию — сгенерированный ИИ код без понимания = 0 баллов (силлабус §6).

## 4. Конфликты
Один Issue — один исполнитель (или пара). Перед PR обновитесь из `upstream/main` и разрешите конфликты сами. Не трогайте чужие файлы без нужды.
